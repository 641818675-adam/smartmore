# PartFinder Mobile 架构设计与演进规划

版本：10.0.0　　目标设备：三星 Galaxy Z Fold3（兼顾直板机与平板）

---

## 1. 问题与目标

桌面版 PartFinder V9.6（PySide6 + SQLite）是选型工作的主工具，但销售在客户现场
只能用手机。此前已有一版移动端（Kotlin + Jetpack Compose），评价是"不好用"。

复盘后的判断：**问题不在技术栈，而在设计出发点**。旧版把桌面版的模块
（选型 / 对比 / 客户 / 设置）搬到手机上，本质是一次"界面移植"。而销售在现场的
真实动线是：

| 场景 | 动作 | 时长预期 |
|------|------|---------|
| 客户报出竞品型号 | 查我方对标 + 应对话术 | < 15 秒 |
| 确认某型号料号 | 搜索 → 复制料号 → 发给客户 | < 10 秒 |
| 配一套设备 | 选主机 → 带出线缆配件 → 复制整包 | < 30 秒 |
| 车间无信号 | 全部功能可用 | 100% 离线 |

因此本版以"搜索即首页"重构信息架构，并围绕**复制**这一高频动作设计交互。

---

## 2. 关键约束

约束决定了架构，先列清楚：

1. **构建机无外网**。pip 与 npm 均被代理拒绝，所有依赖必须已在本机或可手写。
2. **Android SDK 无 NDK / CMake**。排除一切需要原生编译的方案。
3. **已有 Gradle 8.14.3 与 AGP 缓存**，但 Gradle 构建仍需联网校验依赖，不可靠。
4. **JDK 17 + aapt2 + d8 + apksigner + zipalign 齐备**。
5. **数据规模小（1213 条，884 KB）**，但要求可扩展到十万级。
6. **Fold3 三种形态**：外屏 331dp 窄长、内屏竖屏 756dp、内屏横屏 944dp。

## 3. 架构决策记录

### ADR-001：应用本体用 Web 单页应用，原生层只做承载壳

**Status**：Accepted

**Context**
候选方案有三：继续 Kotlin/Compose、Flutter、WebView + HTML/CSS/JS。
Flutter SDK 未安装且无法下载，直接排除。Compose 已跑通，但：
- 每轮 UI 调整都要走"改 Kotlin → Gradle 构建 → 装包"的分钟级循环；
- 响应式折叠屏布局在 Compose 里代码量大，且难以精细控制视觉细节；
- 桌面版业务规则已有一份实现，移动端需要第二份，Compose 方案下这份要手写更多。

**Decision**
原生层退化为一个不含业务逻辑的 WebView 壳（约 200 行 Java，零第三方依赖），
应用本体是 `assets/web` 下的单页应用。原生层只提供 Web 拿不到的能力：
剪贴板、持久化、Toast、屏幕 dp。

**Consequences**
- 获得：UI 迭代快、响应式断点用 CSS 表达最自然、视觉细节可控、可无浏览器自测。
- 付出：WebView 首帧略慢于原生（实测数据在 1213 条量级下无感知）；
  剪贴板等能力必须走 JS 桥接，多一层胶水。
- 风险：`file://` 不是安全上下文，Web Clipboard API 与 localStorage 均不可靠——
  已由 ADR-005 化解。

---

### ADR-002：手工驱动 SDK 工具链打包，不用 Gradle

**Status**：Accepted

**Context**
Gradle 方案依赖网络解析依赖，构建一次需 1–3 分钟且可能失败。
而 SDK 自带工具链完整：aapt2 compile/link、javac、d8、zipalign、apksigner。

**Decision**
`build.py` 直接用 Python 驱动上述工具，九个步骤全部离线完成，
产出对齐并签名的 release APK。

**Consequences**
- 获得：构建约 5 秒、完全离线、可复现、产物 80 KB。
- 付出：不支持 R 类资源引用（Java 侧不引用任何资源，规避该限制）；
  新增第三方库需手工处理 dex 合并——当前零依赖，暂无影响。
- 取舍说明：这是"可逆性优先"的选择。若将来依赖变多，
  可随时切回 Gradle 而不影响 web/ 下的任何代码。

---

### ADR-003：移动端数据为构建期导出的只读快照

**Status**：Accepted

**Context**
桌面版 `products.db`（SQLite）是唯一事实来源。移动端若自带数据生成逻辑，
就会出现两个事实来源，迟早漂移。

**Decision**
`scripts/export_mobile.py` 从 `products.db` 与竞品 Excel 导出
`products.json` / `competitor.json`，作为只读资产打进 APK。
移动端**只消费、不生产**产品数据。

**Consequences**
- 获得：单一数据源；数据更新只需重跑导出 + 重新构建。
- 付出：更新数据必须重新打包安装，不能热更新（演进路线 v10.2 解决）。
- 附带收益：JSON 压缩率极高，884 KB → 37 KB。

---

### ADR-004：搜索引擎移植桌面版分级评分，不引入检索库

**Status**：Accepted

**Context**
桌面版 `search_engine.py` 采用 P0–P6 七级匹配 + NLP 实体加分 + 状态优先排序。
移动端需要一致的结果，否则销售在两套系统间会看到不同答案。

**Decision**
在 `web/js/search.js` 中逐条移植分级规则与排序键，并针对手机输入习惯
增加三项增强：空格分词降级重试、数值语义归一（`5MP` / `500万` → `pixel=5`）、
同义词扩展。全量内存扫描，构建期预生成小写索引串。

**Consequences**
- 获得：与桌面版结果一致；1213 条单次查询 1–6 ms；零依赖。
- 付出：搜索逻辑现在有两份实现（Python / JS），存在漂移风险——
  这是本架构**当前最主要的技术债**，演进路线 v11 解决。
- 性能边界：十万条时全量扫描约 80–300 ms，届时需引入倒排索引（见演进路线）。

---

### ADR-005：持久化走原生 SharedPreferences 桥接

**Status**：Accepted

**Context**
`file://` 页面 origin 为 null，localStorage 在部分 WebView 版本被禁用或清空；
Web Clipboard API 仅在安全上下文可用。收藏与设置若丢失，对现场使用是致命的。

**Decision**
通过 `@JavascriptInterface` 暴露 `getPref / setPref / copy / toast / screenWidthDp`。
收藏、最近查看、偏好设置全部落在 SharedPreferences。
前端保留三级降级：原生桥 → localStorage → 进程内存。

**Consequences**
- 获得：数据可靠、复制即时生效。
- 付出：多一层 API 表面。`addJavascriptInterface` 有安全前提，
  已通过 `setBlockNetworkLoads(true)` 与 URL 白名单收敛风险面。

---

### ADR-006：折叠屏靠"不重建 + CSS 断点"，不依赖折叠特性库

**Status**：Accepted

**Context**
Jetpack WindowManager 能提供铰链位置，但引入依赖且需处理生命周期。
而 Fold3 的三种形态在 CSS 宽度断点上完全可区分。

**Decision**
Manifest 声明全部 `configChanges`，使展开/折叠时 Activity 不重建，
WebView 内滚动位置、搜索词、选中项全部保留。
布局用断点表达：< 600dp 单栏 + 详情全屏层；≥ 600dp 左列表 / 右详情双栏。
铰链位于屏幕中央，恰好落在双栏分栏线附近，内容不被折痕贯穿。

**Consequences**
- 获得：零依赖、状态连续（这是折叠屏体验的关键）、适配任意屏宽而非仅 Fold3。
- 付出：无法精确避让铰链像素位置。当前分栏比（`clamp(300px, 40%, 400px)`）
  已使折痕落在分隔区，实测可接受；若将来出现横向铰链设备需重新评估。

## 4. 系统视图

### 4.1 上下文

```
   销售（客户现场，常无网络）
            │
            ▼
   ┌──────────────────┐
   │ PartFinder 移动端 │  ← APK 完全离线，零网络请求
   └──────────────────┘
            ▲
            │ 构建期导出（单向）
   ┌──────────────────┐
   │ PartFinder 桌面版 │  ← products.db 为唯一事实来源
   │  PySide6 + SQLite │
   └──────────────────┘
```

### 4.2 容器

```
APK
├── Android 壳（Java，零依赖）
│     MainActivity  WebView 承载 + 生命周期 + 折叠不重建
│     Bridge        剪贴板 / 偏好存储 / Toast / 屏幕 dp
└── assets/web（单页应用，无框架）
      ├── index.html   骨架 + 启动屏 + 错误可视化
      ├── css/app.css  设计系统、断点、组件
      └── js/
            search.js    分级检索（移植自桌面版）
            contract.js  选型套包（移植自桌面版）
            data.js      数据加载 + 三级降级存储
            app.js       路由、状态、渲染
```

### 4.3 依赖方向

依赖严格单向，无循环：

```
app.js  →  contract.js  →  search.js
   │           │              │
   └───────────┴────→ data.js ┘
```

业务规则（search / contract）不感知 DOM，可脱离浏览器在 Node 中直接测试——
这是 `tools/test_core.js` 得以存在的前提。

## 5. 质量属性

| 属性 | 现状 | 手段 |
|------|------|------|
| 离线可用性 | 100% | 数据内联为资产；`setBlockNetworkLoads(true)` |
| 检索延迟 | 1–6 ms | 构建期预生成小写索引；全量内存扫描 |
| 启动 | 数据解析一次性完成 | 启动屏 + 全局错误可视化 |
| 状态连续性 | 折叠/展开不丢失 | 全量 configChanges，单 Activity |
| 可测性 | 35 项自动化断言 | 业务层可 Node 直测；渲染层 DOM 模拟自测 |
| 可维护性 | 单向依赖、模块可单独测试 | 分层 + 无框架 |
| 体积 | 80 KB | 零依赖 + JSON 高压缩率 |

## 6. 演进路线

### v10.1 — 离线选型助手
把桌面版 `ai_assistant.py` 的规则化部分（场景 → 推荐型号 → 话术）
移植为本地规则引擎，保持零网络依赖。若将来要接云端大模型，
应作为 **可选增强** 而非依赖，离线路径必须始终可用。

### v10.2 — 数据热更新
当前更新数据要重新打包。改造为：APK 内置基线数据 + 应用启动时扫描
`Download/PartFinder/` 下的新版 JSON，校验版本后覆盖。
这样销售可自行替换数据，不必重装应用。

### v11.0 — 消除双份搜索实现（关键技术债）
当前 `search_engine.py` 与 `search.js` 是同一套规则的两份实现，
规则调整需要同步两处，迟早漂移。建议路径：

1. 把领域逻辑（检索评分、套包规则）抽成纯数据驱动的规则表（JSON）；
2. 桌面版与移动端各自实现极薄的解释器，规则表单一来源；
3. 或退一步：将分级评分规则表化，先消除最易漂移的评分常量。

这一步做完，两个端才真正共享内核，而非共享概念。

### v11.x — 规模演进触发器
当数据量超过 **5 万条** 或单次检索超过 **50 ms** 时，
引入倒排索引（构建期生成 term → material_ids），
把内存全扫描换成索引查找。在此之前不要做——为 1213 条数据建索引是过度设计。

## 7. 风险与边界

| 风险 | 影响 | 缓解 |
|------|------|------|
| 搜索规则双份实现漂移 | 两端结果不一致 | v11.0 规则表化；当前以桌面版为准 |
| WebView 版本差异 | 旧设备样式异常 | minSdk 26；仅用广泛支持的 CSS 特性 |
| 手工打包不支持 R 类 | 新增资源受限 | 架构上不引用资源；真需要时切 Gradle |
| 数据更新需重装 | 运维成本 | v10.2 热更新 |
| 铰链精确避让 | 展开态折痕压内容 | 分栏比已规避；新形态设备需重新评估 |

**非目标（明确不做）**：客户/报价 CRM、云端账号体系、多用户协作。
这些属于桌面版范畴，移动端保持"查询 + 选型 + 话术"的单一职责。
